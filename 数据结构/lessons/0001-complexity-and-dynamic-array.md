## §1 核心认知：结构决定代价

> ◆ **本课唯一必须带走的东西**
>
> **数据结构 = 组织数据的方式，它决定每个操作的代价。学结构之前先学会"数代价"（Big-O），否则永远只能背结论。**

眼见为实。同样"往容器里放 10 万个数"，从尾部放和从头部放，实测差着两三个数量级（§1.1 的 A，你马上自己量一遍）。操作没变、数据量没变，变的只是**数据怎么被组织**——代价就完全不同。

三个推论，每个都值回今天的学费：

1. **标不出复杂度的代码 = 没写懂的代码。**本课程从今天起立一条铁规：**每个方法注释标 Big-O**——它逼你回答"这个操作为什么是这个代价"，答不出就说明结构没吃透。这条纪律贯穿 10 次课，也是判卷的硬门禁。
2. **没有更好的结构，只有更便宜的取舍。**数组随机访问 O(1) 但头部插入 O(n)；后面每种结构在你心里都该是一张"操作 × 代价"的价目表——选型就是对价目表做取舍，这是第 9、10 课设计 LRU 和 KV 缓存的全部本钱。
3. **JS 的数组不是魔法，是别人手写的动态数组。**V8 里它就是一块按需增长的连续内存。今天你亲手重造它——写完再回头看 `arr.push(x)` 那一行，你会知道每次调用在付什么钱、**偶尔**在付什么大钱。

> ⚠️ **本课避坑**
> 建立"数代价"的意识后，别走另一个极端——"O(n) 不好，处处要 O(1)"。n = 100 的数组线性扫一遍比什么都快，Big-O 只在 **n 变大时**说话（§2.1 细说）。先简单、再正确、后优化——"数据量一百条也要上树"是路线图点名的头号常见错误。

### §1.1 动笔预测（8 分钟）

别只看。下面 4 个实验，**先把预测写下来**（写在 `hello.ts` 底部注释里就行），再跑代码对答案。预测用"倍数关系 / 数量级"表述，不用秒——不同机器秒数不同，数量级才是通用语言。计时用 `performance.now()`（Node 全局就有，不用 import）。

**A. 尾部 vs 头部**：`push` 10 万次和 `unshift` 10 万次，耗时差多少倍？

```typescript
const N = 100_000;
let t0 = performance.now();
const a: number[] = [];
for (let i = 0; i < N; i++) a.push(i);
const tPush = performance.now() - t0;

t0 = performance.now();
const b: number[] = [];
for (let i = 0; i < N; i++) b.unshift(i);
const tUnshift = performance.now() - t0;

console.log(`push:    ${tPush.toFixed(1)} ms`);
console.log(`unshift: ${tUnshift.toFixed(1)} ms（${(tUnshift / tPush).toFixed(0)} 倍）`);
```

**B. 清空一筐**：把 10 万元素的数组清空——从头 `shift` 和从尾 `pop` 各花多久？差多少倍？（代码仿 A 自己写，量出来才有发言权）

**C. 查找**：10 万个数各灌进一个数组和一个 `Set`，各查 1 万次"某数在不在"（`includes` vs `has`）——差多少倍？

**D. 单次 push 的耗时曲线**：给 100 万次 `push` 逐次计时，把耗时超过均值 10 倍的"尖刺"挑出来（每圈 `t0 = performance.now(); arr.push(i); times.push(performance.now() - t0)`，最后扫一遍 times）。两个问题：尖刺占多大比例？它们的位置是均匀分布，还是越来越稀疏？

写完预测再对照（数字为备课实测，2026-09-09 本机；你的机器秒数会不同，数量级应一致）：

> [!success]- 对照答案（先写完预测再展开）
> **A：约 400 倍。**实测 push ≈ 1.4 ms，unshift ≈ 558 ms。push 尾部落座一步到位；unshift 要让现有全体后挪一位——第 i 次 unshift 搬约 i 个元素，总共搬 0+1+…+99999 ≈ 50 亿次。O(n) 对 O(n²)，总账差一个数量级，总量再乘一个数量级。
>
> **B：同款灾难，约 600 倍。**实测 shift ≈ 558 ms、pop ≈ 1 ms。shift 和 unshift 是一家人（都在头上动土），pop 和 push 是一家人（都在尾巴上落座）——**从哪头动土，决定要不要全员搬家**。
>
> **C：约 130 倍、差两个数量级。**实测 includes ≈ 74 ms、Set.has ≈ 0.6 ms。数组 includes 每次从头扫到尾，1 万次 × 最多 10 万个 ≈ 十亿次比较；Set 靠哈希函数直接算出"该去哪找"，均摊 O(1)。第 7 课你亲手造这个哈希表。
>
> **D：尖刺极少、越来越稀疏。**实测 100 万次 push 中尖刺仅 359 个（0.036%）；前三十来个的位置是 0、1、227、358、554、658、848、967、1289、……、9970、11174、13130——间隔越拉越开。绝大多数 push 快得像免费的；偶发贵几十倍的那些，是**座位满了、全员搬家的时刻**。但每搬一次家，容量上一个台阶，离下一次搬家就更远。**把这个现象记住：§2.5 的均摊分析就是它的数学版；任务 2 你会亲手造出同样的尖刺。**

## §2 看清你写下的东西（30 分钟）

学前阅读讲"Big-O 是什么"。这一节讲手册不会直说的事：Big-O 到底在数什么、数组凭什么快、JS 哪些方法在暗处收费、push 偶尔贵一下怎么记账。

### §2.1 Big-O 数的是"基本操作执行了多少次"

**不是数循环层数，是数次数；次数由什么决定，复杂度就由什么决定。**

三条规则够用一整课：

| 规则 | 例子 | 结论 |
| --- | --- | --- |
| 顺序段相加，取最大 | O(n) 的循环后接 O(n²) 的循环 | 整体 O(n²)——小头被大头淹没 |
| 嵌套相乘 | 外层 n 次 × 内层 m 次 | O(n·m)——两个变量独立时就都留着 |
| 扔掉常数和低阶项 | 2n+8、n²/2+3n | O(n)、O(n²)——Big-O 谈增速，不谈秒数 |

第 3 条最容易犯嘀咕：n²/2 怎么敢把 /2 扔了？因为 Big-O 回答的是"**n 翻倍时，时间翻几倍**"——n²/2 在 n 翻倍后是原来的 4 倍，n² 也是 4 倍。常数不改变"翻倍的翻倍法"。同理，§1.1 A 里 50 亿次搬运的精确值不重要，重要的是它是"随 n 平方增长"的。

一套三个词：**最好 / 最坏 / 平均**。线性查找：最好 O(1)（第一个就是）、最坏 O(n)（在最后或压根不在）、平均扫一半 n/2 → O(n)。工程上**默认标最坏**——把丑话说在前面；除非另注（比如哈希的均摊，§2.5）。

### §2.2 数组的内存模型：一排连续的座位

数组在内存里是**一排连续的座位**。这一条物理事实，推导出它的全部价目：

- **随机访问 O(1)**：`a[i]` 的地址 = 起点地址 + i × 每座宽度——一次乘法一次加法，直达。第 0 个和第 1000 万个，一样快。这就是 §0.3 里 `scores[2]` 一步到位的原因。
- **中间插删 O(n)**：往第 3 座插一个人，第 3 座起全体后移一位；最坏插头部，全员搬家。§1.1 A 的约 50 亿次搬运就是它。
- **缓存友好（概念级）**：CPU 读内存按块预读，连续的座位一次捎带一整块——这是数组实战中常比复杂度同级的链表更快的原因之一，第 2 课链表出场时回来对照。

而 JS 的 `[]` 并不是"散落各处的对象"——V8 给它配的是真正的**动态数组**：一块按需增长的连续内存 + 长度。你今天手写的 `DynamicArray`，就是它的骨架。

### §2.3 JS 数组的暗价目表

| 方法 | 直觉以为 | 实际 | 干这活该用谁 |
| --- | --- | --- | --- |
| `push` / `pop` | O(1)？ | **均摊 O(1)**（§2.5） | 就是它 |
| `shift` / `unshift` | O(1)？ | **O(n)**，全员搬家 | 第 3 课的手写队列 |
| `splice(i, n)` | "删几个而已" | **O(n)**，后面全体前移 | 视场景 |
| `includes` / `indexOf` | "查一下" | **O(n)**，从头扫 | `Set.has` / `Map.get`（第 7 课造） |
| `sort` | ？ | **O(n log n)** | 内建已优好 |

> ⚠️ **暗价的连锁反应**
> 表里最危险的不是某个方法，是**它出现在循环里**：一层循环 × 每次 O(n) 的方法 = O(n²)——代码看起来"就一层 for"，实际上每圈都在全员搬家。ex1 的第 6 段就是这个陷阱：先在纸上摔这一跤，好过在生产里摔。

### §2.4 capacity 与 length：预订的座位 vs 坐下的人

两个数字，从今天起必须分开叫：

- **length（长度）**：用户视角——现在装了几个元素。`arr.length` 给你看的就是它。
- **capacity（容量）**：实现视角——内存里实际预订了几个座位。座位可以空着，但搬家按整张桌子算。

动态数组的核心戏法一句话：**座位满了，换一张两倍大的桌子，全员搬过去。**贵（一次 O(n)），但买断了"接下来很久都有座"。为什么翻倍不是 +1？+1 的话每次 push 都满座都搬家，n 次 push 总搬家 O(n²)；翻倍则总共只搬约 2n 人——下一条细算。

### §2.5 均摊分析：把偶发的贵，摊到每次操作上

push 的三种标法，一个都不能混：

- **最好 O(1)**：还有空座，直接落座。
- **最坏 O(n)**：正好这次满了，全员搬家。
- **均摊 O(1)**：**总账算法**——从空数组连续 push n 次，搬家发生在容量 1、2、4、…、n/2 各档口，总搬家人数 = 1 + 2 + 4 + … + n/2 < n；加上 n 次落座本身，总代价 ≈ 2n～3n 次基本操作。**总账 ÷ 次数 = O(1)。**

§1.1 D 的实测就是这套账的实物版：359 个尖刺摊进 100 万次 push，平均每次还是快得像免费的。

> ⚠️ **均摊 ≠ 平均**
> 平均（average）对**随机输入**求期望——"数据长什么样的概率各半"；均摊（amortized）对**确定的操作序列**记总账——"最坏的那次确实贵，但贵得足够稀疏"。push 的最坏 O(n) 从不消失，它只是被摊薄了。这两个词面试常混着考，现在就把界限画清。

### §2.6 Python 对照表

你的 Python 直觉大多能迁移，两个最值钱的对照已加粗：

| JavaScript | Python | 代价 |
| --- | --- | --- |
| `arr.push(x)` / `arr.pop()` | `list.append(x)` / `list.pop()` | 均摊 O(1) / O(1)——**两边都是动态数组，同款戏法** |
| `arr.shift()` | **`list.pop(0)`** | O(n)——**Python 官方文档劝你改用 `collections.deque`** |
| `arr.includes(x)` | `x in lst` | O(n) |
| `set.has(x)` | `x in s` | 均摊 O(1) |
| `map.get(k)` | `d[k]` | 均摊 O(1) |

> [!tip]- resize 定成 private，测试怎么观察扩容？
> private 的 resize 是内部机关，外界不该手动掰它。但 `capacity` getter 是公开的：测试里把座位 push 满，再 `expect(arr.capacity).toBe(8)`——**从外部可见的行为观察内部发生的变化**，正是"测行为不测实现"（TS 第 8 课的老话，这门课每课都用）。

> [!tip]- insert 的"整体后移"从哪头开始挪？
> 从**尾巴**开始：最后一个先挪到 length 位置，然后倒数第二个、倒数第三个……最后腾出 index 的座位放新人。反过来从 index 开始挪，会把还没挪走的人直接覆盖掉。"挪错方向丢数据"这个坑，第 2 课链表还有续集（"先接新、再断旧"）。

> ✅ **检查点（比写完代码更重要）**
> ① `new DynamicArray<number>(2)` 连 push 3 个后：capacity 变 4，且 get(0)、get(1) 还是最初两个值（搬家没丢人）；② get(-1)、get(越界)、pop 空数组、insert(越界) 全部 throw，没有一处静默返回 undefined；③ 演示区输出与注释里的预期逐行一致；④ `npx tsc --noEmit` 沉默 + `npx vitest run` 全绿 + 全程无 as / !。

规则：**合上代码**，先在心里把答案完整说出来，再点开折叠对照。"感觉我知道"不算数。答完之后，把三道复盘问题口述成文字发给我，我来判卷：

自测五题（每题先默答，再点开「看答案」）：

**Q1. 两层嵌套循环一定是 O(n²) 吗？**

> [!question]- 看答案（先默答再点开）
> **不一定。**乘法规则是"外层次数 × 内层次数"，关键看内层跑了多少：内层跑常数次 → O(n)；内层跑 i 次（三角嵌套）→ 0+1+…+(n-1) = n(n-1)/2 → 扔掉 1/2 还是 O(n²)；内层由另一个变量 m 决定 → O(n·m)。**每次见到嵌套，只问一句：内层次数由什么决定。**

**Q2. capacity 和 length 有什么区别？谁是用户可见的？**

> [!question]- 看答案（先默答再点开）
> **length 是坐下的人数（用户视角），capacity 是预订的座位数（实现视角）。**用户只见 length；capacity 是动态数组的实现细节，决定下一次 push 要不要搬家。底层数组的物理长度等于 capacity，但有效元素只有前 length 个——**越界判断用 length，不是底层数组的长度**。

**Q3. 为什么扩容翻倍，而不是每次 +1？**

> [!question]- 看答案（先默答再点开）
> **+1：每次 push 都满座、都搬家，n 次 push 总搬 1+2+…+n ≈ n²/2 → O(n²)。翻倍：搬家只在容量 1、2、4、… 档口发生，总搬家 < n → 均摊 O(1)。**就差在"新桌子订多大"这一个决定上，一个 O(n²) 一个均摊 O(1)。

**Q4. 最好 / 最坏 / 平均 / 均摊，四个词各在说什么？均摊和平均差在哪？**

> [!question]- 看答案（先默答再点开）
> **前三个对"一次操作"说话**：这一次输入最好怎样、最坏怎样、随机输入的期望怎样（线性查找：O(1) / O(n) / O(n)）。**均摊对"一串操作"记总账**：最坏那次确实贵，但贵得稀疏——总账 ÷ 次数。平均是概率的期望，均摊是序列的总账；push 是"最坏 O(n)、均摊 O(1)"的经典样本。

**Q5. `includes` 查 1 万次和 `Set.has` 查 1 万次差在哪？凭什么 Set 快？**

> [!question]- 看答案（先默答再点开）
> **includes 每次从头扫到尾，O(n) × 1 万次；Set.has 哈希直达，均摊 O(1) × 1 万次——实测约 130 倍、两个数量级（§1.1 C 你亲手量过）。**凭什么：数组用"位置"组织数据，找值只能扫；Set 用"计算"换"索引"，哈希函数直接算出该去哪找。这个戏法第 7 课你亲手造一遍。
