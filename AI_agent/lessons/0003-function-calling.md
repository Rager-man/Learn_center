## §1 核心认知：模型只递申请单，干活的手永远是你的

> ◆ **本课唯一必须带走的东西**
>
> **模型只输出"调用参数"，执行永远是你写的代码。**模型看到你的数学题，不会去"算"——它递出一张申请单（`tool_calls`：调哪个工具、参数是什么），然后停下（`finish_reason: "tool_calls"`）。**算的人是你的代码**。算完，你把结果作为一条新消息发回去，模型这才第一次看见答案，再把它总结成"人话"给你。从"模型说话"到"模型驱动代码"，中间隔着两张单子：一张它递给你（tool_calls），一张你递回给它（role: "tool"）。

眼见为实。这是真实响应（导师预检实测，glm 系同款结构）：

```jsonc
{
  "finish_reason": "tool_calls",     // ← 不是 "stop"——模型没"说完"，它要借你的手
  "message": {
    "role": "assistant",
    "content": "",                   // ← 空！答案不在 content 里
    "reasoning_content": "……思维链……",  // ← glm-5.3-flash 强制思考，照常计费
    "tool_calls": [{
      "id": "call_00_R0VczY……",      // ← 工单号，回传结果时靠它对号
      "type": "function",
      "function": {
        "name": "calculator",        // ← 要调谁
        "arguments": "{\"expression\": \"123*456\"}"   // ← 字符串！长得像对象的字符串
      }
    }]
  }
}
```

两句话自检方向感（第 1 课你在这里翻过车，先站稳）：

- ✗ "模型算出了 123×456 等于 56088，然后告诉我。" ——错，它没算，也算不对大数。
- ✓ "模型递了张申请单：请用 calculator 算 `123*456`。**我的代码**算出 56088，把结果发回去——模型第二次发言时，才第一次看见这个数。"

三个推论，今天 80 分钟里反复会用到：

1. **申请单 ≠ 结果。**tool_calls 里只有"调谁 + 什么参数"，没有结果——执行权 100% 在你手里，模型永远摸不到你的机器。这就是"让模型驱动你的代码"：它出意图，你出手。
2. **arguments 是 JSON 字符串，内容不可全信。**又是第 2 课的"长得像数据的文本"——`JSON.parse` 这道门照样要过，参数照样要校验（模型会递 `"hello*3"` 这种单子）。兜底肌肉一条不浪费。
3. **没发的，等于不存在。**模型看见执行结果，要等你把 `role: "tool"` 消息发回去——在那之前它只知道"我递过单子"，不知道算出来是多少、还是根本炸了。第 1 课的核心认知在工具世界原样成立。

> ⚠️ **本课避坑：原样 append，别手工重拼**
> 回传结果时，带 tool_calls 的 assistant 消息要**整个对象原样** push 回 messages。手工拼 `{ role: "assistant", content: "" }` 会丢掉 `tool_calls`（模型不记得自己递过单——直接 400 或行为错乱）和 `reasoning_content`（智谱官方明文要求保留，见 §2.5）。一条姿势永绝后患：**模型给什么，你 append 什么，一个字段都不动。**

### §1.1 动笔：预测时序（5 分钟）

你问"123 乘以 456 等于多少？"，到模型说出"56088"为止——**凭直觉写下完整过程**：总共几次 HTTP 请求？每一步是谁在干活（你 / 模型 / calculator）？messages 数组每步之后长什么样？写完再去对照 §2.1。

> [!success]- 对照答案（先写完再展开）
> **两次 HTTP 请求，中间夹一次你的代码执行，messages 从 1 条涨到 3 条：**
> 1. 发出 `[user 问题]` + tools 说明书（第 1 次请求）
> 2. 收到申请单：finish_reason = `"tool_calls"`，messages 还是你发的那 1 条
> 3. **你的代码**：parse arguments → calculator 执行（纯本地，0 请求）
> 4. append 申请单 assistant 消息（原样）+ tool 结果消息 → messages 3 条
> 5. 再发（第 2 次请求）→ 模型看见结果 → content 给出答案，finish_reason = `"stop"`
>
> 预测里少算了一次请求、或把"执行"记在模型头上，都正常——§2.1 的全景图就是给你校准的。

## §2 知识讲解：一次往返的完整解剖（20 分钟）

### §2.1 全景时序：两次请求夹一次你的代码

```
你(程序)                     模型(API)                calculator(你的代码)
   │ ① user:"123×456?"          │                          │
   │   + tools 说明书(schema)     │                          │
   │ ─────────────────────────▶  │                          │
   │                             │ ② 递申请单(不下场算)        │
   │ ◀─────────────────────────  │   tool_calls + 空content   │
   │                             │                          │
   │ ③ JSON.parse(申请单参数)      │                          │
   │ ─────────────────────────────────────────────────────▶ │ ④ 执行 = 56088
   │                             │                          │    (或 throw)
   │ ⑤ push 申请单消息(原样)        │                          │
   │   push role:"tool"(结果)     │                          │
   │ ─────────────────────────▶  │ ⑥ 模型这才看见结果          │
   │ ◀─────────────────────────  │ ⑦ content:"…56088"        │
   │   finish_reason:"stop"       │                          │
```

| 步 | 谁在干 | 干了什么 | messages 此刻 |
| -- | ---- | ------ | ------------ |
| ① | 你 | 发 user 问题 + **tools 说明书** | 1 条 |
| ② | 模型 | 不作答，递申请单（`finish_reason:"tool_calls"`） | 还是 1 条 |
| ③ | 你 | parse arguments + 校验 | 1 条 |
| ④ | **你的代码** | calculator 真正执行（唯一一次真计算，纯本地） | 1 条 |
| ⑤ | 你 | append 申请单（原样）+ tool 结果（带工单号） | 3 条 |
| ⑥⑦ | 模型 | 看见结果，总结成答案（`finish_reason:"stop"`） | 3 条 |

看清这个结构：**一次"完整往返" = 两次 API 调用 + 一次代码执行**。它是 agent 的原子操作——第 4 课的 agent loop 就是把这个往返套进 while，让模型自己决定"继续递单子"还是"收工总结"。

### §2.2 tools 说明书：schema 的三块各写给谁看

请求体里加一个 `tools` 数组（智谱官方示例，OpenAI 兼容格式）：

```jsonc
"tools": [{
  "type": "function",
  "function": {
    "name": "get_weather",                    // ← 给你的注册表对号用
    "description": "获取指定城市的当前天气信息",    // ← 给模型看：我是谁、什么时候该用我
    "parameters": {                           // ← 给模型看：填表格式（JSON Schema）
      "type": "object",
      "properties": {
        "city": { "type": "string", "description": "城市名称，例如：北京、上海" }
      },
      "required": ["city"]
    }
  }
}]
```

三块各司其职：`name` 是工单和派活的对接暗号；`description` 是**写给模型看的广告词**——模型挑不挑你的工具、参数填得对不对，八成取决于这段话（第 5 课的主课，今天先写"够用"版）；`parameters` 是 JSON Schema 子集，`type/properties/required` 三件套够用，还能用 `enum` 限定取值。

### §2.3 申请单里有什么、没什么（复盘题 2 的答案从这里长出来）

**有的：**

| 字段 | 是什么 | 你拿它干什么 |
| ---- | ----- | ---------- |
| `id` | 工单号 | 回传 tool 消息时 `tool_call_id` 带上它，对号入座 |
| `type` | 恒为 `"function"` | 认脸用 |
| `function.name` | 要调谁 | 查你的注册表 |
| `function.arguments` | 参数，**JSON 格式字符串** | `JSON.parse` + 字段校验（第 2 课肌肉） |

**没给你的三样（每样都是坑）：**

1. **执行结果**——当然没有，还没执行呢。谁执行？你。
2. **参数合法性**——模型会递 `"hello*3"`、会编你不认识的字段。parse 成功只是及格线。
3. **多张单子的先后依赖**——一次响应可能带多条 tool_calls（比如先查时间、再算时间差）；谁依赖谁，模型在单子里没写，编排实际由你的多轮往返决定（任务 2 第 9 题专门观察这个）。

### §2.4 你的 calculator 要过的三道关（JS 特色课）

工具是你写的，坑也是你踩的。calculator 三行代码就能跑，但今天测试集里埋了三道题，对应三道关：

| 关 | 题目 | JS 的坑 | 对策 |
| -- | ---- | ------- | ---- |
| 1 白名单 | "把 hello 乘以 3" | 模型会硬凑 `hello*3` 递进来 | 正则白名单：只放行 `数字 空白 + - * / ( ) . ^`，其余一律拒绝 |
| 2 翻译 | "计算 2 的 64 次方" | JS 的 `^` 是**按位异或**——`2^64` 静默算成 66，错得毫无声响 | 求值前把 `^` 全换成 `**` |
| 3 除零 | "123 除以 0" | JS 的 `123/0` 是 `Infinity`，**不报错**——比崩溃更阴险 | 求值后 `Number.isFinite` 检查，不过关就 `throw new Error("除数为零")` |

姿势：白名单过了再交给 `new Function("return (" + 表达式 + ")")` 求值——**永远不要把模型给的原文直接 eval**（智谱官方示例自己都在用 eval + 白名单，那是弱防护，你至少把白名单做严）。另记一笔：JS Number 的精度边界是 2^53，`2**64` 算得出但不精确（尾巴错了）——工具价值那道题的答案会"对但不准"，先记下现象，§5 学有余力用 BigInt 治。

**工具报错怎么办？——第 2 课回传修复的直系应用。**

```typescript
// 第 2 课：messages = [……, 坏输出 assistant, 报错 user]     → 教模型认错
// 今  天：messages = [……, 申请单 assistant, 报错 tool]       → 同款模式，换了角色名
try {
  result = calculate(args.expression);
} catch (e) {
  result = `工具执行出错：${e instanceof Error ? e.message : String(e)}`;   // ← 不裸崩、不吞，喂回去
}
messages.push({ role: "tool", tool_call_id: tc.id, content: result });
```

工具炸了，程序不崩、错误不吞——把报错原文回传，让模型自己决定下一步：换个参数重递？换个工具？还是告诉用户"这题我不会"？**这正是第 2 课判卷时你欠的第 5 级"放弃策略"的 agent 版**：明确的失败结果交给上层（现在是交给模型）处理，而不是炸穿主循环。

### §2.5 智谱的规矩（2026-09-03 依据官方文档核实 + 导师预检实测）

| 事项 | 智谱 GLM 的规矩 |
| ---- | -------------- |
| tools 格式 | OpenAI 兼容：`type:"function"` + `name/description/parameters`（JSON Schema） |
| tool_choice | **默认且仅支持 `auto`**（官方原文）——挑工具完全是模型自主决策 |
| 一次多单 | 无 `parallel_tool_calls` 参数；但一条响应可能带多条 tool_calls——逐张执行、逐张 append tool 消息 |
| arguments | 官方原文"工具调用参数（JSON 格式字符串）"——parse + 校验，没有商量 |
| 回传顺序 | **先** append 带 tool_calls 的 assistant 消息，**再** append `role:"tool"`（`tool_call_id` 对号），然后第二次请求 |
| reasoning_content | 思考模式文档原文："**必须显式保留 Reasoning content，并在返回工具结果时一并返回**"；且"不要重新排序或修改，否则会降低效果并影响缓存命中" |

> [!tip]- 导师预检实录（2026-09-03，DeepSeek 线实测——智谱同姿势）
> 开课前导师用探针跑了一遍完整往返：`finish_reason:"tool_calls"` → content 空串 → arguments 是 JSON 字符串 → 回传 → `"stop"` + 正确答案，全通。顺手做了个实验：**故意丢掉 reasoning_content 回传——没有报 400，模型照样答对了。**但别高兴：官方警告的是效果下降与缓存失效，"没炸"不等于"没错"。规矩就一条：**原样 append 整个 message 对象**，一条姿势两家通吃。（速查表 §3.1 旧说法"漏传直接 400"已按本次实测修正。）

### §2.6 观察方法论：expect 是锚点，不是答案

任务 2 的 12 题测试集，每题带 `expect`（期望的选择）和 `note`（观察点）。三条纪律：

1. **expect 不是标准答案**——`1 + 1` 那题模型自己算、调工具、拒答，各有各的道理，记下它的实际行为就行。
2. **归因分两类**：实际选择和 expect 对不上时，先问"**我的工具描述写清楚了吗**"，再问"模型错了吗"。九成"模型选错"，病根在 description。
3. **今天只记录，不优化**——忍住别改描述刷分。把素材攒全，第 5 课带着这份记录回来做"描述改写 A/B 对比"，那才是主课。

### 任务 1 · calculator 单次往返（50 分钟）

打开 `02_ToolUse/ex4_tool_call.ts`——一句剧本：**让模型借你的手，算一道数学题。**

**第 1 步（10 分钟）· 先看申请单**：填 TODO 1——把 `CALCULATOR_SCHEMA` 两处 description 改写成你自己的说明书（结构不用动）。然后只在 `main()` 里写 ①② 两步（发问题、打印 `finish_reason` 和整个 message），先跑一次——**亲眼看四件事**：`finish_reason` 变了、`content` 是空的、申请单躺在 `tool_calls` 里、`reasoning_content` 陪着它。

**第 2 步（20 分钟）· 写三道关**：填 TODO 2——白名单、`^`→`**` 翻译、除零检查（§2.4 的表照着过）。写完先别发请求，本地自测三条：`calculate("(17+3)*12-8/2")`、`calculate("2^64")`、`calculate("hello*3")`——最后一条该拿到一句报错，不是崩溃。

**第 3 步（20 分钟）· 走完五步**：填 TODO 3——parse arguments（记得它刚才是字符串）→ 执行（try/catch 包住，报错当结果）→ **原样** append 申请单消息 + tool 结果消息 → 第二次请求 → 打印最终答案。这次 `finish_reason` 应该是 `"stop"`。

> ✅ **检查点（比写完代码更重要）**
> 终端输出逐行过一遍，能指着说：**这行是模型在干活、这行是我的代码在干活**；`"tool_calls"` 和 `"stop"` 两个 finish_reason 都亲眼见过。说不出来，回到 §2.1 的表对一遍再继续。

### 任务 2 · 双工具选择观察（30 分钟）

**第 1 步（10 分钟）· 第二张申请单**：填 TODO 4——`get_current_time` 的 schema（无参数工具，`properties` 留空对象）和实现。返回格式要"信息够用"：日期 + 星期 + 时刻（只返回 `"14:30"` 的话，第 12 题就缺原料了）。再把注册表 `TOOLS` / `REGISTRY` 搭起来——两张单子都从这一处派活。

## §4 复盘：10 分钟检索练习

规则不变：**合上代码**，先在心里完整说出来，再点开下方折叠对照。答完把三道复盘问题的口述答案发给我，我来判卷：

1. 画出单次 tool call 的完整时序图：谁在什么时候做了什么？
2. tool_calls 里模型给了你什么？没给你什么？
3. 如果工具执行报错，此刻模型知道吗？——它什么时候才会知道？

自测五题（每题先默答，再点开「看答案」）：

**Q1. `finish_reason` 变成 `"tool_calls"` 时，答案在 content 里吗？调用信息在哪？**

> [!question]- 看答案（先默答再点开）
> **不在。content 是空串或 null——模型"还没说完话"。调用信息在 `message.tool_calls`：id（工单号）、function.name（调谁）、function.arguments（参数，JSON 字符串）。**

**Q2. 拿到 `function.arguments` 之后，第一件事干什么？为什么参数"天生是数据"还要做这件事？**

> [!question]- 看答案（先默答再点开）
> **`JSON.parse` + 字段校验。**
>
> "天生是数据"说的是协议层：参数走专用通道、不裹围栏不带闲话——这比 prompt 里求 JSON 可靠得多。但 arguments 本体是 JSON 格式**字符串**，且内容不可全信（模型会递 `hello*3`、会编字段）——第 2 课的 parse 与校验肌肉原样复用。

**Q3. role:"tool" 消息靠什么和申请单对上号？漏了它会怎样？**

> [!question]- 看答案（先默答再点开）
> **`tool_call_id`，值取自申请单的 `id`。**
>
> 一次响应可能多张单子，每张的执行结果都是独立的 tool 消息——没有工单号，模型（和 API 校验层）就不知道哪份结果对应哪张单。

**Q4. 回传结果前，messages 里必须先 append 什么？为什么强调"原样"？**

> [!question]- 看答案（先默答再点开）
> **模型那条带 tool_calls 的 assistant 消息，整个对象原样 push——然后才是 tool 消息。**
>
> "原样"两个字防两个丢：丢 `tool_calls`（模型不记得自己递过单）和丢 `reasoning_content`（智谱官方要求必须保留并一并返回，重排或修改会降效果、伤缓存）。手工重拼 `{role:"assistant", content:""}` 是本课头号坑。

**Q5. 第 10 题（123 除以 0）你的 calculator 抛错了——此刻模型知道吗？它什么时候才知道？**

> [!question]- 看答案（先默答再点开）
> **不知道。工具在你机器上执行，模型看不见。**
>
> 要等你把报错文本作为 tool 消息 append 进 messages 并发起第二次请求，模型才第一次知道"炸了"——然后自己决定下一步。没发的，等于不存在。
