## §1 核心认知：窄化 = 逐个回应"可能没值"

> ◆ **本课唯一必须带走的东西**
>
> **strict 下满屏的 null/undefined 报错不是找麻烦，是编译器在指出"这里可能没值"。窄化（narrowing）就是你逐个回应它的过程。**

开场先做个检索练习。第 2 课里，`| undefined` 在你眼前出现过**三次**——先别往下读，自己数：都是哪三处？

> [!success]- 数完再展开
> 1. 访问 `contact.phone`（可选属性，`phone?: string` 访问出来是 `string | undefined`）；
> 2. `contacts.find(...)` 的返回值（找不到时是 undefined，签名如实标注）；
> 3. `update` 里的 `old`（同上，找不到要改的人）。
>
> 三处长相不同，说的是同一句话：**这里可能没值**。第 2 课你只体验了"编译器拦你"，今天学怎么回应它。

你还在第 2 课复盘时说过一句话（判卷时我们一起校正过的那个版本）：

> **"判断值在不在——类型永远是同一个联合，判断的是此刻它落在哪一半。"**

这句话就是窄化的**定义**，原样抄进本课。而且其中一招你早就会了——`if (contact)`，第 2 课 update 里你无师自通写的。今天要做的只是把这一招扩展成整套工具箱：

```typescript
const found = contacts.find(c => c.id === 1);   // found: Contact | undefined
found.name;            // ✗ error TS18048: 'found' is possibly 'undefined'.
                       //   编译器：它可能没值，你凭啥直接点？

// 回应它：确认值在，我才用
if (found) {
  found.name;          // ✓ 这个分支里 found: Contact——编译器亲耳听见你确认了，按 Contact 检查
}
```

三个推论，今天反复会用到：

1. **窄化不是新语法，是控制流里的证明。** `if` / 提早 `return` / 三元——都是给编译器看证据的方式。证据成立的那段代码里，类型就收窄成"有值的那一半"。
2. **编译器只认它自己能验证的证据。** 它顺着代码执行的路逐点记录"此刻这个变量是什么"（所以叫控制流分析）。你在函数外面、注释里、心里的口头承诺，它一概不认——想硬塞给它，就是 `as` 和 `!`（§2.5 讲为什么今天禁用）。
3. **满屏红的正确姿势是逐条回应，不是镇压。** 逐条读报错 → 问"这里谁可能没值" → 选工具回应。删类型、写 any、拍个 `!` 让它闭嘴——都不是回应，是把风险调成静音：错了一样在运行时炸（第 1 课"声称 vs 事实"，这里再兑现一次）。

> ⚠️ **本课避坑**
> `as` 和 `!` 今天**全程禁用**。不是它们没用，是你现在练的正是"回应"的肌肉——每想敲一次 `!`，就少问一次"谁可能没值"。逃生舱的合法场合 §2.5 有说明书，今天先收起来。

### §1.1 动笔预测（5 分钟）

老规矩，**先别用 IDE**。假设已有（注意小美的 `nickname` 是空字符串——不是缺席，是"注册了但没填"）：

```typescript
interface Student { name: string; nickname?: string; scores: number[]; }
const roster: Student[] = [
  { name: "小钟", nickname: "老钟", scores: [88] },
  { name: "小美", nickname: "",    scores: [0] },

const mailbox = new Map<number, string>();
```

逐段预测：`npx tsc --noEmit` 报不报错？报的话是什么？跑起来呢？

```typescript
// A —— 问号加上了，应该安全了吧
const len: number = roster[0].nickname?.length;

// B —— 两行都能过编译；跑起来 a、b 各是什么？
const a = roster[1].nickname || "匿名";
const b = roster[1].nickname ?? "匿名";

// C —— 同一个 s，两行 console.log
const s = roster.find(x => x.scores.length > 0);
if (s) {
  console.log(s.name);    // ← 第 1 行
}
console.log(s.name);       // ← 第 2 行

// D —— Map 里查一个人

console.log(email.toUpperCase());
```

写完再对照（猜错很正常，错在哪就是哪没懂）：

> [!success]- 对照答案（先写完再展开）
> **A：只编译错，跑起来不炸。**`error TS2322: Type 'number | undefined' is not assignable to type 'number'.`——`?.` 保证**点的瞬间不炸**（小钟有昵称，运行时一切正常），但它的**结果**是 `number | undefined`：万一没昵称，整条表达式就是 undefined，还是塞不进 `number`。所以 `?.` 不是"变出值来"，是"把风险从点的瞬间挪进结果的类型里"。想让结果确实是 number，得再配一个兜底：`roster[0].nickname?.length ?? 0`——正是复盘题 1 那行。
>
> **B：都编译过；`a` 是 "匿名"，`b` 是 ""（问的是小美的空昵称）。**编译器对两行都沉默——这是运行时才分胜负的暗战。`||` 认 6 种"假值"（`false` / `0` / `""` / `null` / `undefined` / `NaN`），空字符串被它当"没有"；`??` 只认 `null` / `undefined` 两种真正的"没值"。空字符串是"有值，只是不体面"——该不该当"没有"，是业务决策，不是运算符默认（§2.1 展开）。顺带一提：若换成 `roster[0]`（小钟，昵称"老钟"非空），两行结果相同、都是 "老钟"——`||` 和 `??` 的差别，只在左边是空字符串、0 这样的假值时才显现。
>
> **C：第 1 行不红，第 2 行红。**`if (s)` 里面这个分支，编译器看着你确认过，`s` 就是 `Student`；出了 if，承诺作废——`error TS18048: 's' is possibly 'undefined'.`（你可能猜到了：这和 A 的关系是——窄化只活在控制流里）。**每个使用点，都得站在证明的下游。**
>
> **D：两行都红，但报错码不同。**直连点那行：`error TS2532: Object is possibly 'undefined'.`；先存变量再点那行：`error TS18048: 'email' is possibly 'undefined'.`——同一个病（`Map.get` 找不到键返回 undefined），两身制服。码不用背，认得"possibly 'undefined'"这个病名就行。
>
> 四段合起来：`?.` 管**点的瞬间**，`??` 管**没值时的兜底**，`if` 管**接下来一段路**，精确比较（§2.2）管**只排除没值、放行 0 和 ""**。四件工具全在为同一句话服务：把"可能没值"安抚成"确定有值"，再动手。

## §2 看清你写下的东西（30 分钟）

学前阅读讲"每个语法是什么"。这一节讲五件手册不会直说的事：两个空值运算符的分工与边界、窄化工具箱怎么选兵器、证据在哪些情况下会"过期"、两个高产制造 `| undefined` 的 API、以及 `as` / `!` 的使用说明书。

### §2.1 `?.` 与 `??`：两个专门对付"没值"的运算符

**`?.` 可选链**：`a?.b` —— a 是 null/undefined 时，整条链**就地短路**成 undefined，不再往下走；否则照常取 `a.b`。链可以串：

```typescript
order?.customer?.address?.city
// 中途任何一环没值 → 整条表达式就是 undefined；全都有值 → city 的值
```

两个手册不强调的细节：

- **短路是物理性的**：`a?.b.c()` 在 a 没值时，`.c()` 根本不执行——后面那串里就算藏着函数调用、副作用，也一个都不发生。注意短路的触发点只有一个：**`?.` 前面那一环**——中间用 `.` 连接的环节没值**不会**短路，想连它一起保得再写一个 `?.`（如 `a?.b?.c()`，§4 自测 Q1 专考这个坑）。Python 对照：它就是 `a and a.b and a.b.c` 这条链的安全语法版。
- **`?.` 只许用于读取**。写 `box.inner?.v = 1` 会被语法层直接拒绝：`error TS2779: The left-hand side of an assignment expression may not be an optional property access.`——想想也合理：inner 没值的话，这 1 要赋给谁去？想写它，先用 if 确认 inner 在。

**`??` 空值合并**：`a ?? b` —— a 是 null/undefined 才取 b，其余一律 a。和 `||` 的分工一张表看清（y 是兜底值）：

| `a` 的值               | `a ｜｜ y` | `a ?? y` |
| -------------------- | -------- | -------- |
| `""`（空字符串）           | `y`      | `""`     |
| `0`                  | `y`      | `0`      |
| `false`              | `y`      | `false`  |
| `NaN`                | `y`      | `NaN`    |
| `null` / `undefined` | `y`      | `y`      |

`||` 把六种假值一锅端；`??` 只接 null / undefined 两行。三个要点：

- **Python 老兵的秘密**：`a or y` 在 Python 里同样吞 0 和 ""——这个坑你不是没见过，是换了语言没认出它。`??` 才是 `a if a is not None else y` 的直译。
- 什么时候**反而**该用 `||`：业务上"空字符串就该当没填"时（比如昵称 `""` 视同匿名）。可以，但那是你**说得出理由的业务决策**，不是默认习惯。
- 两个不许裸混：`a ?? b || c` 直接编译错（`error TS5076: '??' and '||' operations cannot be mixed without parentheses.`）——委员会怕你分不清优先级，索性禁了，要混必须自己加括号表态。

### §2.2 窄化工具箱：五件日常兵器

| 兵器     | 长相                          | 适合判断什么                    | Python 对应                     |
| -------- | ----------------------------- | ------------------------------- | ------------------------------- |
| 真值窄化 | `if (x)` / `if (!x)`          | 顺带把 undefined 和假值一起挡  | `if x:`                         |
| 精确比较 | `if (x !== undefined)`        | 只排除"没值"，0 / "" 放行       | `if x is not None:`             |
| typeof   | `if (typeof x === "string")`  | 原始类型的联合                  | `isinstance(x, str)`            |
| in       | `if ("email" in x)`           | 对象身上有没有这个属性          | `"email" in x`（字典）——同名同义 |
| instanceof | `if (x instanceof Date)`    | 是不是某个类的实例              | `isinstance(x, datetime)`       |

三句使用须知：

- **真值 vs 精确，是本课最重要的选择题**：`if (x)` 会把 0、""、false 一并当"没值"送进 else。`score?: number` 且 0 是合法分数时，`if (s.score)` 就是 bug——必须 `if (s.score !== undefined)`。任务 1 里有两处病灶专门埋了这个坑的两种长相。
- **`!= null` 是全课程唯一推荐 `==`/`!=` 的地方**：`if (x != null)` 一句同时排除 null 和 undefined（宽松相等只在这一个判空场景下行为正好）。认识它是因为到处会读到；自己写，精确比较也完全够用。
- **typeof / in / instanceof 今天认识长相即可**——它们的主场在第 4 课（判别联合 + 手写守卫），届时你会天天用。

### §2.3 窄化只活在控制流里

编译器做的是**控制流分析**：沿着代码执行的路，逐点记录"此刻这个变量是什么"。由此两条纪律：

1. **证明必须写在使用点的上游。** §1.1 的 C 你已经见过：if 外面的 `s.name`，if 里的承诺保不了它。同一个变量，换个位置使用，就要重新出示证据。
2. **两种写法都合法，守门员风格更清爽。** 同一个"查邮箱，没登记就算了"：

```typescript
// 安全区风格：确认了才进去
const email = mailbox.get(id);
if (email !== undefined) {
  return email.toUpperCase();   // 这里面 email: string
}
return undefined;

// 守门员风格：没值的先请出去，主逻辑不缩进
const email = mailbox.get(id);
if (email === undefined) {
  return undefined;             // 没登记：提早退场
}
return email.toUpperCase();     // 走到这里，编译器看着你查过——email: string
```

函数越长，守门员风格越舒服：主逻辑顶着格写，读的人一眼看到"正事"，异常情况全在门口处理完。任务 1 推荐用它。

### §2.4 `find` / `Map.get`：签名如实的两个高产户

```typescript
contacts.find(c => c.id === 1)   // Contact | undefined —— 找不到
mailbox.get(id)                  // string | undefined  —— 键不存在
```

这两个 API 不是"容易出 bug"，恰恰相反——它们是**把"可能找不到"如实写进签名的诚实 API**。对照组里坐着一堆不如它们诚实的：

- `scores[0]`：类型说是 `number`，空数组时实际是 undefined——**签名在撒谎**（第 1 课你亲眼看过 `data.name` 打出 undefined 的那类问题）。
- `findIndex`：找不到给 `-1`——历史包袱，第 2 课见过。

顺带认识签名诚实的下标写法：`scores.at(0)` 返回 `number | undefined`——越界就如实说 undefined，任务 1 有处病灶用它修最顺手。

Python 对照：`d.get(k)` 返回 None——你在 Python 里从不写 `d[k].upper()` 而不查 None，同一份谨慎原样平移即可。TS 多给的一层好处是：**忘了查，编译器替你记得**（TS18048 / TS2532）。

### §2.5 `as` 与 `!`：逃生舱使用说明书

- **`!`（非空断言）**：`found!.name` 读作"我向编译器保证它有值，出了事我负责"。编译器从此闭嘴；运行时错了，TypeError 照炸。
- **`as`（类型断言）**：`found as Contact` 读作"闭嘴，按我说的记"。同样是压嘴，不验证任何东西。

一句话：**它们没消除风险，只是让风险静音。**所以今天的纪律：

1. **任务全程禁用**。每次想敲 `!`，其实是在跳过一次问"谁可能没值"的机会——跳过 30 次，窄化的肌肉就白练了。
2. 逃生舱的合法场合（知道即可，今天和近期都用不上）：测试 / 演示代码里"我知道数据长什么样"的快捷方式；类型迁移中途的临时脚手架（真撞见了我现场讲）。
3. `!` 的底线一句话：**敲下去的那一秒，你要能说出"编译器不知道、而我知道的那件事是什么"。**说不出来，就不是你在用 `!`，是 `!` 在滥用你。

规则同前两课：**合上代码**，先在心里把答案完整说出来，再点开折叠对照。"感觉我知道"不算数——说得出来才算。答完之后，把三道复盘问题口述成文字发我，我来判卷：

3. 什么情况下才"允许"用 `!`？你现在的答案和第 1 次相比有变化吗？

自测五题（每题先默答，再点开「看答案」）：

**Q1. `a?.b.c` 里 a 有值、b 是 undefined——整条表达式的结果是什么？`.c` 会执行吗？**

> [!question]- 看答案（先默答再点开）
> **结果是抛 TypeError，`.c` 会被求值（并且当场崩）。**`?.` 的短路只发生在**它前面那一环**（这里的 a）没值时；a 有值，链条就照常往下走——`a.b` 求值得到 undefined，接着 `.c` 照样执行，炸出 `Cannot read properties of undefined`。类型层面同理：若 b 是可选属性，`a?.b.c` 在编译期就会于 `.c` 处报 TS2532（Object is possibly 'undefined'）——编译器自己都在提醒你 `?.` 只保住了 a 那一环。想让 b 没值时也整串短路，得写成 `a?.b?.c`——"从没值的那环开始后面整串不跑"，只对写了 `?.` 的那些环成立。

**Q2. `0 || "默认"`、`0 ?? "默认"`、`"" || "默认"`、`"" ?? "默认"` 各得什么？**

> [!question]- 看答案（先默答再点开）
> **"默认" / 0 / "默认" / ""。**`||` 认 6 种假值（false、0、""、null、undefined、NaN）一锅端；`??` 只认 null / undefined。0 和空字符串是"有值，只是不体面"——要不要当"没有"，是业务决策，得说得出理由。

**Q3. `if (x)` 到底窄化掉了什么？`score?: number` 且 0 是合法分数，该用哪个判断？**

> [!question]- 看答案（先默答再点开）
> **窄掉全部假值**——undefined、null、0、""、false、NaN 一律进 else。0 合法时必须 `if (s.score !== undefined)`：只排除"没值"，放行"不体面的值"。这就是真值窄化和精确比较的分界线，任务 1 两处静默坑的全部原理。

**Q4. `find` / `Map.get` 的返回类型为什么"悲观"？这是缺点吗？**

> [!question]- 看答案（先默答再点开）
> **因为它们可能找不到——签名如实标注 `T | undefined`。这不是悲观，是诚实**：把"可能找不到"这个运行时事实提前到编译期，逼你在使用点回应一次。对照组：`scores[0]` 空数组时类型照说 number（撒谎）、`findIndex` 给 -1（历史包袱）——签名诚实的 API 才配得上 strict 的保护。

**Q5. `!` 和窄化的本质区别，一句话？**

> [!question]- 看答案（先默答再点开）
> **`!` 转移责任（让编译器闭嘴，运行时风险原封不动）；窄化消除风险（给编译器看它自己能验证的证据，"没值"的路根本走不到使用点）。**用 `!` 的底线：能说出"编译器不知道、而我知道的那件事"——说不出来就是滥用。
